# Data

All data in `public/data/` is **synthetic**. It is generated by `data-gen/generate.py`
(fixed seed, so every run gives the same files).

Its shape is loosely modelled on a real UK battery-electric bus fleet: about 435 buses,
around 57,000 km per bus per year, the mix of work-order types, how concentrated part
usage is, and how costs are spread. All of those values were then rounded and perturbed.
The operator ("Kestrel Bus Group"), depots, models, identifiers, part numbers and prices
are all invented. Nothing in this repo can be traced back to a real operator,
manufacturer or vehicle.

```
python -m pip install -r data-gen/requirements.txt
python data-gen/generate.py            # writes public/data/*.csv
python data-gen/reference_metrics.py   # writes data-gen/expected_metrics.json
```

## Tables

The tables come from two source systems that don't share keys, which is the normal
situation and most of what makes the data hard to use.

| Table | Source | One row per | Key columns |
|---|---|---|---|
| `depots` | Ops | depot | `plant_code`, `eam_go_live` |
| `buses` | Fleet register | bus | `body_number` (manufacturer), `fleet_number` (operator), `model` (`DD` double-deck / `SD` single-deck) |
| `odometer_monthly` | Telematics | bus per month-end | `body_number`, `reading_date`, `odometer_km` (cumulative) |
| `parts` | Manufacturer parts master | part | `part_number`, `component`, `system`, `is_consumable`, `list_price_gbp`, `models`, `superseded_by` |
| `operator_part_xref` | Operator stores | operator part code | `operator_part_code` → `part_number` (blank if unmapped) |
| `workshop_lines` | Operator EAM system | part line on a work order | `wo_ref`, `fleet_number`, `plant_code`, `wo_type`, `operator_part_code`, `qty`, `wo_total_hours` |
| `warranty_claim_lines` | Manufacturer warranty system | part line on a claim | `claim_ref`, `body_number`, `repair_date`, `complaint`, `part_number`, `qty`, `part_cost_gbp` |

How they join:

```
workshop_lines.fleet_number ─────► buses.fleet_number
workshop_lines.plant_code ───────► depots.plant_code
workshop_lines.operator_part_code ► operator_part_xref ─► parts.part_number
warranty_claim_lines.body_number ► buses.body_number       (never customer_fleet_ref)
warranty_claim_lines.part_number ► parts.part_number
odometer_monthly.body_number ────► buses.body_number
```

The workshop data has labour hours but no costs. The warranty data has costs but no
hours. Workshop part costs come from `parts.list_price_gbp`. Warranty labour is estimated
from the median workshop hours for the same component.

## Planted data-quality traps

Each of these comes from something seen in real fleet data. The "effect" column is what
happens if you ignore it, measured on the generated data (seed 2026) by `reference_metrics.py`.

| # | Trap | What goes wrong | Correct handling | Effect if ignored |
|---|---|---|---|---|
| 1 | `wo_total_hours` repeats on every part line of a work order | Labour is double counted | Take hours once per `wo_ref` | 34,743 h instead of 16,981 h (2.0×) |
| 2 | Part lines aren't failures. One repair can use 10 rivets | Failure counts are inflated | One event per work order (or claim) per component | 14,036 corrective lines vs 9,451 events |
| 3 | Consumables (cable ties, coolant, filters) dominate raw counts | The top of the list is clutter | Filter on `parts.is_consumable` | 41% of workshop lines are consumables |
| 4 | Negative `qty` = part returned to stores | A part that wasn't used counts as a failure | Net qty per work order and part, keep if > 0 | 2.5% of work orders have a return |
| 5 | `customer_fleet_ref` on warranty claims is keyed by hand and usually copied from the previous claim | Claims land on the wrong bus, depot and model | Join warranty on `body_number` | 39% of claim lines land on the wrong model |
| 6 | Odometer spikes (a mis-mapped telematics unit) and missing months | Fleet km is overstated, so MDBF looks better than it is | Drop readings above any later reading; spread km across gaps | +14% fleet km, one bus +745% |
| 7 | Depots joined the EAM system on different dates (`depots.eam_go_live`) | Before go-live most failures were never recorded. Rising counts reflect coverage, not reliability | Count only months after go-live, for both km and failures | MDBF 8% too optimistic |
| 8 | Operator part codes were re-coded part-way through ("DO NOT USE - SEE …") | One part's failures are split across two descriptions | Group via the cross-reference to `component`, not description | 11 parts split across two descriptions |
| 9 | The cross-reference is incomplete | Some failures can't be attributed to a component | Show "Unmapped" explicitly; don't drop it silently | 9% of failure events, the largest single bucket |
| 10 | Warranty claims are submitted 3 to 60 days after repair, and the extract was taken 10 July 2026 | The most recent weeks look unusually reliable | End the analysis window at 31 May 2026 | June 2026 has about a third of the claims of earlier months |
| 11 | Work order types for warranty claims exist only as free text (`complaint`) | Breakdown-based MDBF misses warranty breakdowns | Classify the complaint text | 49% of breakdowns appear only on claims |

## Metric definitions

- **Failure event**: a corrective work order (`Breakdown`, `Driver Defect`, `Work Arising`)
  or a warranty claim where at least one non-consumable part was consumed (net qty > 0).
  Preventive maintenance, accident damage, campaigns and pre-EAM parts issues are not
  failures, even when they replace the same parts.
- **MDBF** (mean distance between failures) = km driven ÷ failure events, using the same
  bus-months for both. There are three definitions, because people mean different things
  by "failure":
  - in-service breakdowns only
  - breakdowns plus driver-reported defects
  - all corrective events
- **Component MDBF** = km driven by the models the component is fitted to ÷ events where
  that component was replaced.
- **Analysis window**: each depot's EAM go-live to 31 May 2026.
- **Labour rate**: £45/h, as an editable assumption.

The data only records repairs that consumed a part. A fault fixed by adjustment leaves no
line, so these MDBF figures measure distance between part-replacing events.

## Storylines worth finding

- **Bad batch**: buses in batch `KIN-2024-04` (Kingsway, double-deck) have a door control
  unit that fails about 12 times a quarter, against about 3 a quarter across the rest of
  the fleet. Campaign `C25-03` (May to July 2025) fits the rev B part, and those failures
  stop.
- **Frequency ≠ cost**: seat headrest covers and bell pushes top the failure count. The
  traction battery pack fails 7 times and costs more than any other component.

## Known limitations

- km in a bus's last month can't be recovered if that month's reading is missing. That
  mainly affects buses delivered in 2026.
- Part prices are list prices. Warranty costs are what was claimed, with ±8% variation
  around list.
